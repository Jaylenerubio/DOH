Accessibility Conformance Summary

NYC Health and Affordability Connector prototype — self-service (New Yorker) and CHW channels: intake, dashboard, and the Hospital bills, Health insurance, Eviction, Energy discounts & Tax credits flows

This summarizes the accessibility work built into the prototype and maps it to the success criteria that govern AA conformance for public-sector civic technology. It is a code-level conformance pass, now backed by an automated scan — every interactive control has an accessible name, role, and state; it is not a certified audit. Where something is partial, deferred, or a placeholder, it is marked as such rather than glossed.

Bottom line — the prototype addresses the AA success criteria in code and passes axe-core with 0 violations across 40 page states at phone and desktop widths (see Automated verification). What remains is manual screen-reader testing, the carry-forwards in Known gaps, and the placeholders the vendor must replace in the production build.

Updated Oct 14, 2026 — reflects the self-service channel: home → programs → privacy → contact (returning-client check) → contact method → dashboard, with sign-in by one-time code, a header Menu / language panel, a profile page, dashboard status chips, and “View details” handoff views. Rows marked self exist only in the self-service channel; CHW only in the staff channel.

1.3.12.4.42.4.63.2.5

Supporting structure & announcements

Landmarks & headings

Every page exposes a banner header, a <main id="main"> region and (where present) a labelled Progress region; section titles are <h2>s and every question group is a <fieldset>/<legend>, giving a navigable outline. axe reports no content outside a landmark.

1.3.12.4.1

Status messages

A shared polite live region (A11y.announce()) voices state changes with no focus move — “Copied”, the record-check outcome, a language choice, the next program being started.

4.1.3

State not by colour alone

Selected chips change border and weight; dashboard status is a text chip plus a dated sentence; the current language is tinted and checked; a completed handoff step is checked and reworded.

1.3.11.4.1

Focus management

Validation errors move focus to the offending control; Edit moves focus to the first editable field; opening a header panel moves focus into it and closing returns it to the button; the searchable combobox keeps focus in its input while the list is open.

Page titles — the two-tone treatment & color contrast

Several titles pair a black primary line with a muted grey secondary line (the dashboard and the “What’s next” screens on every program). The grey is presentational only — the title is a single real <h1> with the muted phrase as an inline <span>, so structure survives for assistive tech. Every text color clears the 4.5:1 AA minimum for body text.

The muted grey was deliberately darkened from #939393 (which failed at ~3:1) to #767676 so the two-tone titles meet 1.4.3 Contrast (Minimum) exactly. Dashboard card descriptions and status lines use #565656 at 18px. Only two font weights are used (400 / 600); no bold.

03

“Continue” is never disabled — errors explain themselves

Gated “Continue” buttons don’t use the native disabled attribute — which drops a control out of the tab order and leaves it silent. They stay enabled; an incomplete step is answered with an inline message instead of a dead button.

How it works

Pressing Continue (or Send code / Verify) on an incomplete step calls A11y.stepError(): a visible role="alert" message appears (“Select at least one option to continue”, “Enter the 6-digit code we sent you”, …), the alert text is announced, and focus moves to the offending control. Making a valid choice hides the message. Multi-field forms use per-field aria-invalid + aria-describedby instead.

3.3.13.3.24.1.2

Why not native disabled?

A natively-disabled button is removed from focus order and announces nothing, so a screen-reader user can’t discover it or learn why they’re blocked. Keeping the button live and answering with a message keeps the block discoverable and self-describing.

2.1.14.1.3

Native disabled is reserved for genuine bound-limit or inert controls: the stepper’s − at 0 and + at 8 (20% opacity), and screened program cards in the CHW channel.

04

The rest of the AA story

Beyond the three areas above, the prototype addresses the operable and perceivable criteria that a full AA review checks.

One unified focus ring

Every control shares a single focus indicator (--focus-ring: 3px brand #225E7C, 2px offset, ~7:1 on white), including the header panels and language rows.

2.4.71.4.11

Keyboard operable

All flows work by keyboard, including the header panels (Tab loop, Esc), the searchable combobox (type to filter, ↓/↑, Enter, Esc) and the multi-select program list, which stays open between picks. No keyboard traps: a modal panel always has a reachable Close.

2.1.12.1.2

Reduced motion

prefers-reduced-motion removes the interstitial fades, the hamburger/translate icon morph and panel slide, slows the spinner, and disables card press scaling. All nav motion is 0.3s on one easing curve; nothing flashes.

2.3.3

Target sizes

Buttons and chips are ≥54px tall; stepper ± 56px; header Menu / English / nav links and “Back to dashboard” 44px; language rows 44px; pill remove 44×44; only the “copy” affordance (65×39) sits between the 24px minimum and 44px.

2.5.8

Reflow & resize

Chips share a row at equal widths and wrap when a label would truncate; the dashboard goes from one column to two at 768px; header panels are full-screen at every width; no horizontal scroll at 320px.

1.4.41.4.10

Names match visible text

Buttons whose visible label changes (Copy → Copied, Menu → Close, English → Close, Edit → Done, Start → Finish your application) keep the accessible name in sync because the visible text is the name.

2.5.3

Identity is never shown in full

Sign-in and returning screens show only the last four digits of a phone or the last two letters of an email plus the domain. Not a WCAG criterion, but it keeps screen-reader output from reading a full identifier aloud in public.

—

Timing

Interstitials auto-advance after ~1.5s but carry no interaction, and the one-time code “expires in 10 minutes” wording is copy only — the prototype never times a user out.

06

Automated verification

Run Oct 14, 2026 with axe-core 4.10.3 in headless Chromium (Playwright), rule set wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa, best-practice, at 390×844 and 1280×800. The session was seeded as a signed-in self-service client with every program chosen so that all dashboard states, handoff views and the not-eligible pages rendered.

Result

0 violations on 40 page states × 2 viewports, plus the dashboard with the Menu panel open and with the language panel open. The only remaining flag is the best-practice region rule on the searchable combobox while its list is open (the listbox is portaled to <body>); it is not a WCAG failure.

Fixed during the scan

Progress bars sat outside any landmark (now a labelled region on 15 pages) · sign-in Back was an <a> outside <main> (now a button) · the language combobox left aria-expanded on a role-less wrapper (critical 4.1.2) · the Welcome-back <h1> carried role="status" (now wrapped) · profile and intake-review fields had a conflicting autocomplete="off" (1.3.5).

An automated scan catches roughly a third of WCAG issues. Manual screen-reader and keyboard passes (VoiceOver on iOS and Safari, NVDA on Windows) remain the next step and belong to the vendor’s build, where the markup is final.

07

Known gaps, placeholders & vendor hand-off notes

Stated plainly, because credible conformance means naming what isn’t done. None of these block the AA baseline in the prototype; each must be resolved in the production build.

  • Partial

    Skip-to-content link. Not present; #main targets are on every page, so the vendor should add a visible-on-focus “Skip to main content” link as the first focusable element (completes 2.4.1).

  • Partial

    Translation. The language panel stores and announces the choice but the prototype has no translated strings; the button keeps reading “English”. In production the choice must switch the page language and set <html lang> (3.1.1).

  • Partial

    Consistent help (3.2.6). 311 appears on the not-eligible pages and the Eviction handoff only. If a help mechanism ships (311 line, chat), it needs the same place on every page.

  • Partial

    Stacked logo. PNG at 30px; “Health” renders at ~9px, at the DOHMH 8pt floor. Swap to SVG from comms and verify legibility on device.

  • Placeholder

    Links the vendor must replace. Energy discounts: the Benefits Enrollment Assistance intake URL (#bea-partner-intake-placeholder, flagged in scripts/pillars.js and eeap-next.html). Hospital bills: “Start your application” opens dollarfor.org, a stand-in for the simplified-application link. The privacy-policy link on the privacy page is href="#". The Dollar For / CSS links (Hospital bills review) and the TSU link (Eviction review) are final.

  • Placeholder

    Demo data. Enrollment-site names, addresses, hours and phone numbers; the returning-client demo record; and the hidden Health insurance consent subtext are fictional stand-ins. None are real people or numbers.

  • Depends on partner feed

    “Submitted” state. The dashboard only shows “Submitted” / “received” wording when the partner confirms receipt; until that feed exists the applied state reads “started” and “Awaiting response”. The ?demo=submitted flag exists only to preview the state.

  • Deferred

    Manual audit. Automated scan is clean; a defensible AA claim still needs VoiceOver / NVDA testing on the production markup, plus a check of the live regions in the header panels and interstitials with a real screen reader.
